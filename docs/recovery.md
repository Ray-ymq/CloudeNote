# 备份与故障恢复

Git 历史能找回修改或删除的内容，但不能替代磁盘损坏后的独立备份。云笺不强制推送、不重写历史、不清理可达提交或快照标签，服务器仍需备份完整裸仓库。客户端也应备份知识库及 `.git`，因为未推送提交和操作保护副本可能只存在于当前设备。

单文件恢复在历史中输入文件路径，选择修改或删除前的提交，确认内容后进入恢复预览。整库恢复从快照选择目标，预览新增、覆盖和删除，确认后创建新的恢复提交，再同步传播到其他设备。两种恢复都先保存当前修改，选择恢复前保存的提交即可再次恢复撤回，未完成冲突必须先处理或取消。

服务端备份应包含对象、分支、标签及配置，可在短暂禁止 SSH Git 写入的维护窗口复制整个裸仓库，或使用存储一致性快照。应在备份副本上运行 `git fsck --full` 校验，并存放到独立磁盘或存储。恢复服务器时先保留现有仓库副本并确认权限，让客户端重新测试和预览，不用强制推送覆盖仍可追溯的提交。

## 写入保护

正式写入前，插件在 `.git/cloudnote/operations/<操作ID>/backup/` 和 `staging/` 保存原内容与待写入内容，再保存 `operation.json` 和活动 `journal.json`。替换时还把实际原文件移动到 `displaced/`，以便保留已经打开的文件句柄上的后续写入，再通过不覆盖现有文件的原子硬链接发布新内容；因此知识库所在文件系统需要支持同卷硬链接（如 NTFS、APFS）。准备全部副本后逐个写入并校验，最后推进分支，下一次任务会先恢复活动日志，尚未推进时撤回插件已写入且未被继续编辑的内容。

若中断后用户又编辑了文件，插件保留新编辑并报告原内容副本的位置。数字文件名对应 `operation.json` 中 `changes` 数组下标，可据记录中的路径与哈希另存比较；不要在需要恢复或仍有活动日志时删除保护目录。第一版不自动清理这些副本，释放空间应先备份，确认无活动任务后自行处理。

进程中断可能留下 `.git/cloudnote/task.lock`，其中保存任务进程 ID。下次任务确认旧进程退出后会回收锁；若系统复用进程 ID 或锁损坏，应关闭相关 Obsidian 窗口并确认无任务运行，再人工删除该单个锁文件。任务运行期间不得删除锁，以免多个进程同时写入。

## 故障重试

SSH 或断网失败会保留本地内容和已创建提交。先确认 Agent、主机指纹、Git 所用 SSH 和远端地址，再测试连接并重试，插件不会交互输入密码或绕过主机校验。推送竞争最多自动重新获取并重试三次，仍失败时等待人工重试，不重复提交已有内容。

磁盘不足或权限失败会停止写入并尝试按日志恢复，应释放空间或修复权限后再操作。恢复本身若也失败，应保留整个 `.git/cloudnote` 并根据活动日志人工处理，不能执行破坏性重置。若外部工具改变分支、受管标记或历史，先备份完整目录并恢复一致状态，再继续同步。
